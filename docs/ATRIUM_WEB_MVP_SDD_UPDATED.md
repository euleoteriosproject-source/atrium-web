## 0. Purpose of this document

This document is the **single source of truth** for the first public web MVP of Atrium.

Its purpose is to let an implementation agent build the product **without redefining product, positioning, UX, scope or architecture**.

When implementation convenience conflicts with this document, this document wins unless an explicit product decision updates it.

The MVP exists to validate one business chain:

```text
visitante
  -> reconhece uma dor
  -> inicia diagnóstico
  -> recebe valor
  -> vira lead
  -> vai para WhatsApp
  -> conversa comercial
  -> proposta
  -> cliente
```

The MVP is **not** the full Atrium platform.

# 1. Product vision

## 1.1 What Atrium is

Atrium is a technology company focused on solving operational problems through software, digital experiences, automation, integrations and applied AI.

Institutional positioning:

> **Tecnologia que transforma operação em resultado.**

Commercial interpretation:

> **Primeiro entendemos o problema. Depois escolhemos a tecnologia.**

Atrium should feel like a combination of:

- senior technology consulting;
- premium software delivery;
- automation and integration capability;
- product thinking;
- responsible use of AI.

It must **not** feel like:

- a generic digital agency;
- a cheap freelancer landing page;
- a hype-driven AI consultancy;
- a software factory selling hours;
- a personal developer portfolio.

---

## 1.2 MVP goal

The primary goal is:

> **Generate qualified commercial conversations for Atrium at zero mandatory monthly infrastructure cost during validation.**

The primary business metric is:

> **Qualified commercial conversations generated by the website.**

Secondary metrics:

- diagnostic start rate;
- diagnostic completion rate;
- result-to-lead conversion;
- lead-to-WhatsApp handoff rate;
- proposal rate;
- close rate;
- recurring pain patterns found across leads.

Page views and visual praise are not success metrics by themselves.

# 2. MVP principles

## 2.1 Scope principle

> **Começar pequeno, provar valor e escalar com controle.**

No feature may enter MVP merely because it would be useful in a future platform.

A feature enters MVP only if it materially helps one of the following:

1. attract the right visitor;
2. make the visitor recognize a meaningful problem;
3. deliver useful diagnostic value;
4. qualify the opportunity;
5. preserve the lead;
6. move the opportunity to a human conversation;
7. increase trust enough to support conversion.

---

## 2.2 Zero-cost principle

The MVP must have **R$ 0/month mandatory infrastructure cost** while usage stays inside free-tier limits.

Approved initial services:

- static hosting: Netlify is the current deployment target;
- alternative hosting: Cloudflare Pages or Vercel if required;
- database: Supabase Free;
- server-side form processing: Supabase Edge Function;
- anti-bot: Cloudflare Turnstile Free;
- analytics: Cloudflare Web Analytics;
- conversion channel: WhatsApp deep link.

A custom domain is optional and treated separately from infrastructure cost.

The application must remain portable if any provider changes pricing or free-tier rules.

---

## 2.3 Human-first principle

Atrium does not promise to replace people.

The website should consistently communicate:

> **Tecnologia elimina trabalho que não precisa ser manual e preserva o humano onde contexto, julgamento e relação geram valor.**

---

## 2.4 Technical honesty principle

The site must not recommend AI by default.

It must be acceptable for the diagnostic result to say:

> “IA não parece ser a prioridade neste momento. Uma automação ou integração convencional provavelmente resolve primeiro o principal problema.”

This is a commercial trust advantage, not a weakness.

# 3. Target market and ICP

## 3.1 Primary ICP

Brazilian small and medium businesses that are already operating but have accumulated operational friction.

Typical profile:

- approximately 3–50 people;
- decision maker is owner, partner, director, commercial manager or operations manager;
- business already has customers and real processes;
- uses WhatsApp, spreadsheets, email and/or business software;
- depends on repetitive tasks or disconnected tools;
- has little or no internal technology team;
- can perceive technology as an investment, not only a cost;
- has a problem it may want to improve within the next 1–6 months.

High-interest operational patterns:

- lead-heavy services;
- commercial operations;
- customer service operations;
- real estate;
- B2B services;
- consultancies;
- education/services businesses;
- financial/correspondent/credit-related operations when legally and professionally appropriate;
- businesses whose processes rely heavily on WhatsApp.

Atrium is horizontal in V1. Do not position the public site as exclusive to any one vertical.

---

## 3.2 Low-fit profiles for V1

Do not optimize for:

- someone only looking for the cheapest website possible;
- commodity e-commerce implementation;
- very large projects requiring a full dedicated team;
- 24x7 mission-critical systems requiring operational support Atrium cannot yet provide;
- payment processing core;
- medical record systems;
- projects requiring storage of highly sensitive documents;
- regulated core banking/financial infrastructure;
- vague “build me an Uber” requests;
- projects whose scope clearly exceeds a side-business operating model.

Low fit does not mean the visitor must be rejected by the site. It only affects internal lead qualification.

# 6. Brand and design direction

## 6.1 Brand personality

Atrium should feel:

- modern;
- technological;
- SaaS-ready;
- serious;
- elegant;
- trustworthy;
- human;
- technologically prepared;
- discreet;
- transparent;
- sophisticated without being ostentatious.

## 6.2 Color tokens

```text
brand-navy:       #071832
brand-blue:       #1677FF
brand-blue-deep:  #1757E8
brand-cyan:       #27C8F5
brand-off-white:  #F8F9FC
gray-bg:          #F2F3F5
gray-text:        #566171
```

The canonical brand gradient is `#27C8F5 -> #1677FF -> #1757E8`.

Blue and cyan are the official brand accents. The former gold system must not remain as a competing accent. Product components must consume semantic accent, focus, link, selection and on-dark tokens instead of coupling behavior to a raw brand color.

## 6.3 Visual anti-patterns

Do not use:

- neon;
- purple/cyan AI gradients;
- robots;
- glowing brains;
- rockets;
- fake dashboards;
- generic smiling stock teams;
- exaggerated glassmorphism;
- excessive particles;
- “AI revolution” aesthetics;
- excessive gradients;
- visual noise.

## 6.4 Premium feeling should come from

- typography;
- whitespace;
- hierarchy;
- rhythm;
- precise animation;
- calm contrast;
- strong copy;
- custom diagrams;
- subtle details;
- high-quality responsive behavior.

## 6.5 Typography

Preferred starting direction:

- UI/display sans: **Manrope**;
- optional editorial serif accent: **Source Serif 4**;

Fonts must be loaded efficiently and should not materially harm performance.

## 6.6 Layout

Desktop:

- max content width: 1200–1280px;
- 12-column grid;
- generous vertical spacing.

Mobile:

- 4-column conceptual grid;
- touch-first interactions;
- no desktop-only information architecture.

## 6.7 Motion

Use restrained motion.

Typical durations:

- microinteraction: 180–240ms;
- section motion: 280–450ms;
- complex diagram transition: max ~650ms where justified.

Respect `prefers-reduced-motion`.

No animation should delay conversion or content comprehension.

## 6.8 Official mark and brand assets

The official Atrium mark is a stylized ribbon-like `A`, crossed by a forward arch that completes the letterform. Its geometry follows the approved September 2026 reference and must not be replaced by a generic letter `A`.

The horizontal logo combines the official mark with the geometric `ATRIUM` wordmark. The wordmark is represented as stable vector geometry and does not depend on a remote font.

Canonical reusable assets:

```text
public/brand/atrium-logo-horizontal-on-dark.svg
public/brand/atrium-logo-horizontal-on-light.svg
public/brand/atrium-mark-on-dark.svg
public/brand/atrium-mark-on-light.svg
public/brand/external/atrium-whatsapp-avatar-1024.png
```

Application metadata assets:

```text
app/favicon.ico
app/icon.svg
app/apple-icon.png
app/opengraph-image.png
```

Application rules:

- use the horizontal `on-light` logo on off-white or similarly light surfaces;
- use the horizontal `on-dark` logo on navy or similarly dark surfaces;
- use the isolated mark only where the horizontal lockup is not appropriate, such as favicons and square avatars;
- keep the mark gradient and wordmark contrast intact;
- do not recolor the mark with the retired gold palette;
- preserve clear space and do not distort the SVG aspect ratio;
- keep the SVG decorative when a surrounding link already provides the accessible name;
- use a navy, symbol-only, wide-safe-area square asset for WhatsApp Business;
- use the navy Open Graph composition with the official mark and wordmark, without invented slogans.

### Minha empresa é pequena. Faz sentido?

> Sim. Pequenas operações muitas vezes sentem ainda mais o impacto de tarefas repetitivas, ferramentas desconectadas e processos dependentes de poucas pessoas.

> Sim. Essa é a abordagem preferida da Atrium.

# 10. Diagnostic product specification

The diagnostic is the core differentiator of V1.

It must feel like a short guided consultation, not a survey.

## 10.1 UX rules

- one primary question per screen;
- clear progress indication without fake precision;
- generally 8–12 answered questions per visitor;
- optional questions must be clearly optional;
- mobile-first;
- touch targets >= 44px;
- keyboard accessible;
- answers stay in browser until explicit lead submission;
- result is shown before contact capture;
- preserve state in `sessionStorage`;
- no mandatory account;
- no AI/LLM dependency;
- all logic deterministic and testable.

---

## 10.2 Diagnostic state model

```ts
type Goal =
  | 'SALES'
  | 'CONVERSION'
  | 'AUTOMATION'
  | 'SERVICE'
  | 'WEBSITE'
  | 'SOFTWARE'
  | 'INTEGRATION'
  | 'AI'
  | 'DISCOVERY';

type OpportunityDimension =
  | 'digital'
  | 'sales'
  | 'service'
  | 'automation'
  | 'integration'
  | 'software'
  | 'ai';

type DiagnosticState = {
  version: string;
  startedAt: string;
  primaryGoal?: Goal;
  additionalGoals: Goal[];
  segment?: string;
  companySize?: string;
  acquisitionChannels: string[];
  tools: string[];
  answers: Record<string, unknown>;
  opportunityScores: Record<OpportunityDimension, number>;
  aiRiskScore: number;
  calculator?: {
    people?: number;
    minutesPerDay?: number;
    daysPerWeek?: number;
    estimatedMonthlyHours?: number;
  };
};
```

# 20. Opportunity scoring

Scores are evidence counters, not scientific maturity scores.

Normalize each dimension after all answered questions.

Recommended initial normalization:

```ts
function opportunityLevel(score: number): 'LOW' | 'MODERATE' | 'HIGH' {
  if (score >= 7) return 'HIGH';
  if (score >= 4) return 'MODERATE';
  return 'LOW';
}
```

Thresholds must be configurable in a data module, not hard-coded across components.

Only show up to three main opportunities.

Selection rules:

1. sort dimensions by score descending;
2. exclude dimensions with no meaningful evidence;
3. apply AI risk adjustment;
4. prefer distinct actionable opportunities over redundant categories;
5. if top scores are tied, prioritize primary goal relevance;
6. always allow “no strong opportunity detected” if evidence is weak.

Never fabricate urgency or savings.

# 21. AI priority adjustment

let aiAdjusted = aiScore;

## 23.4 Contact form input hardening — masks, limits and normalization

The contact form must not accept unbounded or ambiguously formatted user input.

This is a **data-quality, UX and security requirement**, not a cosmetic enhancement. Client-side formatting improves usability, but the server remains authoritative for validation and normalization.

### 23.4.1 Implementation order

Implement this hardening in the following order:

1. centralize field constraints and allowed values;
2. implement pure formatting/normalization helpers;
3. apply native input attributes (`type`, `inputMode`, `autoComplete`, length limits) where appropriate;
4. add the WhatsApp/phone mask and paste handling;
5. add clear field-level validation messages;
6. mirror the important constraints in the Edge Function/server schema;
7. add unit tests and real mobile tests for typing, paste, backspace, invalid input and submission.

Do not rely only on HTML `maxLength`. Limits must also be enforced by the validation schema/server. Do not silently truncate invalid server payloads.

### 23.4.2 WhatsApp / phone

V1 is Brazil-first. The contact phone field must:

- use `type="tel"`;
- use `inputMode="tel"`;
- use `autoComplete="tel"`;
- present a Brazilian-friendly mask while typing, e.g. `+55 (51) 99999-9999`;
- accept paste with or without `+55`, spaces, parentheses or hyphens;
- prevent unlimited digit entry;
- after removing formatting and an optional `+55`, accept only a plausible Brazilian national number of 10 or 11 digits;
- normalize the value before persistence/handoff to digits in international form (`55` + national number);
- never persist the visual mask as the canonical phone representation;
- preserve intuitive cursor, backspace and paste behavior;
- display a specific validation message instead of a generic submit failure.

The mask is presentation only. The server must reject phone values outside the same normalized limits even if the request bypasses the browser.

### 23.4.3 Name and company

No visual mask. Apply explicit limits and normalization:

- `name`: required, trim, 2–80 characters;
- `company`: required, trim, 2–120 characters;
- preserve legitimate accents, hyphens, apostrophes and business punctuation;
- do not accept whitespace-only values;
- do not silently cut values that exceed the limit.

### 23.4.4 E-mail

E-mail remains optional. When present:

- use `type="email"`;
- use `inputMode="email"` where supported;
- use `autoComplete="email"`;
- trim surrounding whitespace;
- enforce a maximum of 254 characters;
- validate format client-side and server-side;
- do not apply a visual mask.

### 23.4.5 Selects, consent and non-visible fields

- timeframe and budget must accept only declared enum values;
- consent must remain an explicit boolean and must never be pre-checked;
- honeypot and attribution fields must also have server-side size limits even though they are not normal visible inputs;
- unknown enum values must be rejected, not coerced to a default.

Attribution is auxiliary and must not block an otherwise valid commercial submission. An attribution field above its limit is discarded as a whole; it is never silently truncated into a different value. Only the allowlisted source/UTM/referrer/landing fields are captured, and arbitrary query parameters or PII are not copied into attribution.

### 23.4.6 Accessibility and mobile behavior

- masks must not prevent screen-reader users from understanding the field;
- labels and error messages remain associated with the input;
- mobile keyboard type must match the data being entered;
- validation should happen at useful moments without fighting the user on every keystroke;
- pasted valid phone numbers must be accepted and reformatted;
- error state must not erase user input.

### 23.4.7 Acceptance examples

```text
Phone typed:   51982895068
UI display:    +55 (51) 98289-5068
Canonical:     5551982895068

Phone pasted:  +55 (51) 98289-5068
Canonical:     5551982895068

Too short:     reject with field-level message
Too long:      prevent extra digit entry in UI and reject if bypassed
```

This hardening must be completed **before M6B Admin Lite and before public launch**, so notification/admin workflows consume clean contact data.

### 23.4.8 Database and migration safety

The official physical table remains `public.mvp_leads`.

Migrations that have already been applied must never be rewritten. If M5.1 requires additional PostgreSQL constraints or any other database hardening, implement it through a new additive migration. Do not rename the table, create an alternate physical lead table, or introduce an alias/view for it.

## 26.3 Handoff semantics and tracking

The product distinguishes three independent concepts:

1. commercial stage in `mvp_leads.status`;
2. customer WhatsApp handoff represented by `whatsapp_handoff_at`;
3. human follow-up recorded explicitly by an authorized Atrium administrator.

> **Opening WhatsApp does not mean `CONTACTED`.**

The public post-diagnostic click proves only that the WhatsApp handoff was initiated. It does not prove that a message was sent, delivered, read or answered.

The first click may be tracked asynchronously through the dedicated `track-lead-handoff` Edge Function using the existing browser-held `submissionId` plus `publicCode`. Tracking must be idempotent, must never change commercial status or `last_contact_at`, and must never delay or block opening WhatsApp.

```text
tracking failure -> WhatsApp still opens
```

Admin labels must say clearly whether the visitor opened WhatsApp after the diagnostic, never that the customer contacted Atrium or started a conversation based only on the click.

Status allowed values:

```text
NEW

QUALIFIED
PROPOSAL
WON
LOST
```

Before M6B, status may be updated manually from the Supabase dashboard.

M6B adds only the approved internal Admin Lite workflow. No generic or multi-tenant CRM is built.

For M6B.2, the new timestamp fields above must be introduced only through a new additive migration. Existing applied migrations remain immutable. `internal_notes`, if present historically, is not the operational source for new notes: M6B.2 notes are append-only activities in `public.mvp_lead_activities`.

## 27.2 Commercial status semantics

`public.mvp_leads.status` remains the single source of truth for the current commercial stage:

- `NEW`: captured successfully, with no human contact explicitly recorded by Atrium;
- `CONTACTED`: real human follow-up/contact explicitly recorded by an authorized administrator;
- `QUALIFIED`: human interaction confirmed commercial relevance;
- `PROPOSAL`: proposal sent or presented;
- `WON`: converted into a client/project;
- `LOST`: closed without conversion.

A lead may remain `NEW` after the visitor opens WhatsApp. Delivery of the M6A e-mail and clicking any WhatsApp link also do not imply `CONTACTED`.

The Admin may correct statuses when necessary; V1 does not impose an inflexible one-way state machine. Every real status change must update `status_updated_at` and be auditable in activity history.

## 27.3 Operational timestamps

- `status_updated_at`: latest commercial status change;
- `whatsapp_handoff_at`: first recorded public post-diagnostic WhatsApp opening, using first-write-wins semantics such as `coalesce(whatsapp_handoff_at, now())`;
- `last_contact_at`: latest real human contact explicitly recorded by an authorized administrator;
- `next_follow_up_at`: optional scheduled human follow-up.

For existing records, any backfill must be explicit and semantically justified. If audited records are exclusively test/pre-launch data, `created_at` may be used as the initial `status_updated_at` baseline.

## 27.4 Table `mvp_lead_activities`

M6B.2 introduces the internal append-only table `public.mvp_lead_activities` for an immutable/auditable operational timeline. It is not a generic CRM event platform.

Minimum conceptual schema:

```text
id                uuid primary key
lead_id           uuid not null -> public.mvp_leads(id)
activity_type     text not null
created_at        timestamptz not null
actor_user_id     uuid null
from_status       text null
to_status         text null
note              text null
follow_up_at      timestamptz null
metadata          jsonb null
```

Minimum activity types:

```text
  LEAD_CREATED
  WHATSAPP_HANDOFF
STATUS_CHANGED
CONTACT_RECORDED
NOTE_ADDED
  FOLLOW_UP_SET
FOLLOW_UP_CLEARED
```

New lead creation is recorded as `LEAD_CREATED` by an `AFTER INSERT` trigger in the same transaction as `mvp_leads`. Existing leads receive only an idempotent `LEAD_CREATED` backfill using their factual `created_at`; no other historical action is inferred. Activities cannot be arbitrarily edited or deleted in V1. Corrections are represented by new activities.

Notes are plain text, append-only, length-limited server-side and safely rendered. They must not contain HTML, secrets, sensitive documents or attachments.

## 42.2 External server component

Approved public write paths:

```text
create-lead Supabase Edge Function -> public.mvp_leads
track-lead-handoff Supabase Edge Function -> first whatsapp_handoff_at + one WHATSAPP_HANDOFF activity
```

`track-lead-handoff` is separate from `create-lead` and from authenticated Admin mutations. It accepts only the strict handoff contract, returns no lead details/PII and cannot change commercial status or human-contact timestamps.

Approved asynchronous post-persistence notification path:

```text
public.mvp_leads AFTER INSERT
  -> Supabase Database Webhook
  -> notify-new-lead Supabase Edge Function
  -> Resend
```

The notification path never writes or updates the lead and is not part of the lead-creation transaction.

Approved authenticated Admin paths:

```text
admin-leads        -> read-only lead queries
admin-lead-actions -> typed M6B.2 mutations after validated JWT + UUID allowlist
```

`admin-lead-actions` is not a generic CRUD endpoint. Its initial action allowlist is `CHANGE_STATUS`, `RECORD_CONTACT`, `ADD_NOTE`, `SET_FOLLOW_UP` and `CLEAR_FOLLOW_UP`.

Use simple React state/context or a small store only if complexity justifies it.

Do not introduce Redux.

Diagnostic data model should be data-driven.

#### M6B.2.2 Public `track-lead-handoff`

This function is separate from `create-lead` and all Admin mutation functions. It must:

1. accept only the expected public handoff request;
2. apply exact-origin CORS validation;
3. enforce request size and strict identifier validation;
4. identify an existing persisted lead using both the browser-held random `submissionId` and `publicCode`;
5. verify both identifiers belong to the same lead;
6. idempotently set only the first `whatsapp_handoff_at`;
7. append `WHATSAPP_HANDOFF` exactly once;
8. return only a minimal success/failure DTO with no lead details or PII;
9. never log the request body;
10. never change `status` or `last_contact_at`.

Preferred idempotent update:

```sql
whatsapp_handoff_at = coalesce(whatsapp_handoff_at, now())
```

On `/contato/whatsapp`, the click order is:

1. build and open the customer-to-Atrium WhatsApp URL immediately;
2. start tracking without making navigation depend on it;
3. use a browser-safe fire-and-forget/keepalive mechanism where appropriate;
4. preserve WhatsApp conversion even if tracking fails.

#### M6B.2.4 Admin mutation architecture

M6B.1 `admin-leads` remains read-only. Mutations are isolated in:

```text
admin-lead-actions
```

Security flow:

```text
Admin browser
  -> Supabase Auth JWT
  -> admin-lead-actions
  -> validate JWT server-side through the official identity mechanism
  -> extract validated user.id
  -> exact ADMIN_USER_IDS check
  -> validate typed action and payload
  -> backend-only database operation
```

Authentication is not authorization. E-mail is never an authorization key. The function uses exact CORS allowlists, contains no backend credential in the browser and accepts no arbitrary table/column identifiers.

Initial action allowlist:

```text
CHANGE_STATUS
RECORD_CONTACT
ADD_NOTE
SET_FOLLOW_UP
CLEAR_FOLLOW_UP
```

No generic CRUD endpoint is permitted.

Whenever an action changes `mvp_leads` and appends an activity, both operations must be atomic. Preferred approaches are a small backend-only PostgreSQL function/RPC or another explicit transaction-capable server mechanism. Status/state must never change permanently if its required audit activity fails.

Avoid `SECURITY DEFINER` unless strictly necessary and separately reviewed. Use least privilege and explicit grants.

#### M6B.2.5 Change status

Admin exposes an explicit commercial status control with the existing six statuses. The server must:

- reject invalid enum values;
- reject or explicitly handle no-op changes;
- update `mvp_leads.status`;
- update `status_updated_at`;
- append `STATUS_CHANGED` with `from_status`, `to_status`, validated admin UUID and timestamp;
- keep the lead row and activity atomic;
- support justified corrections rather than impose an overly rigid one-way state machine;
- use confirmation for consequential terminal states where UX warrants it.

#### M6B.2.6 Record human contact

Admin exposes `Registrar contato` through the deliberately small initial contract `publicCode + RECORD_CONTACT`. The server records the current time. Channel, adjustable occurrence time and an optional contact note are not part of the implemented M6B.2 action contract; contextual observations remain append-only `ADD_NOTE` activities.

The action must update `last_contact_at` and append `CONTACT_RECORDED`. When the current status is `NEW`, the operation may atomically transition it to `CONTACTED`; the transition and audit history must be part of the same transaction. A later status must never be downgraded.

Clicking an Admin WhatsApp or e-mail link does not automatically record contact.
